01 — Overview

Not images.
Living code.

Every visual you see in claude.ai — diagrams, interactive charts, animated explainers — is raw SVG markup or an HTML fragment written by the model and rendered natively by your browser. No image generation model is involved at any step.

The core insight

Claude generates <svg> and <iframe srcdoc> the same way it generates Python or JSON — as structured text. The browser paints the result. Quality comes entirely from the precision of the coordinate math and design logic inside the generated code.

What they are

SVG markup or HTML fragments

Raw browser-native code. No canvas API, no image generation, no external rendering service.

How they stream

Token by token over SSE

The response streams as a server-sent events connection. The frontend accumulates the tool call block before rendering.

Where they run

Sandboxed iframe

Set as srcdoc of an iframe with strict sandbox flags — no access to parent page cookies, localStorage, or DOM.

How theming works

CSS variables injected by parent

The parent page injects a stylesheet defining all color variables and class definitions. Dark mode is automatic.

Why this matters for your learning companion

Every mechanism described in this guide is fully reproducible with the Anthropic API. You call the model, parse the code output, render it in a sandboxed <iframe srcdoc>, inject your own CSS variables, and expose a sendPrompt() bridge. No proprietary claude.ai APIs required.

02 — Decision Logic

How Claude decides what to generate

The routing decision runs through four questions in strict order. The first match wins — subsequent checks are skipped.

1
Is a connected MCP tool a fit?
If a connected server (Figma, Amplitude, Hex…) handles the request category → use it. Category match beats aesthetic preference.
e.g. "diagram" + Figma connected → call Figma, not the inline renderer
This is the highest-priority rule. If the user has connected Figma and asks for a diagram, Claude calls Figma — even if the Visualizer could draw something "more illustrative." The user chose to connect that tool. Named servers (explicitly mentioned in the request) are the absolute routing path with no exceptions. An MCP tool failure is reported, not silently substituted.
2
Did the user ask for a file or Artifact?
Keywords: "Artifact", "file", "download", "save as" → produce a downloadable file regardless of content type.
"Show me an Artifact of a green triangle" → file, not inline visual
The word "Artifact" or "file" overrides everything else — even if the content is trivially visualizer-shaped (a bar chart, a simple SVG). The user is explicitly routing to the persistent-file path. "Show me" is a visualizer trigger phrase, but "Artifact" wins.
3
Would a visual genuinely help?
If the task is writing code, drafting an email, answering a factual question, or casual chat → plain text. Visuals only for spatial/relational understanding.
No visual: code help, simple Q&A, summaries, analysis. Visual: concepts, processes, systems, comparisons
The test is whether a picture would help a person understand something they couldn't grasp as well from text alone. "What is photosynthesis?" benefits from a diagram of the mechanism. "What year did photosynthesis evolve?" does not. When in doubt, Claude errs toward visual for anything with spatial, sequential, or relational structure.
4
Does it need interactivity?
Controls, sliders, animations, step-through sequences, live calculations → HTML + JS. Static explanatory diagram → SVG.
HTML: steppers, charts, calculators, simulations. SVG: flowcharts, structural diagrams, cross-sections
The decision rule: does the real system have a control? A water heater has a thermostat — give the diagram a slider. An LLM has input tokens — let the user click one and watch attention weights change. A cache has a hit rate — drag it and watch latency change. If there's something to twiddle, make it twiddlable. Only fall back to static SVG when there's genuinely nothing interactive.
5
Which type of SVG diagram?
Route on intent, not subject. "Document this" → flowchart/structural. "Understand this" → illustrative.
Flowchart: steps/decisions. Structural: containment. Illustrative: mechanisms/metaphors. ERD: Mermaid.js
The most nuanced call. Same subject can produce different diagrams: "transformer architecture" → structural (labelled boxes). "how does attention work" → illustrative (fan of weighted lines between tokens). "how does a hash map work" → illustrative (key falling through funnel into buckets). The illustrative route is the ambitious default for "how does X work" — don't fall back to a flowchart because it's safer.

Learner-platform routing in practice

For an educational agent, the routing above is too generic. These are the subject-specific routing rules that produce the highest learning gain:

Mathematics & calculus
derivatives, integrals, series, limits
▼

Default: HTML with a live graph (Chart.js or D3) that responds to a slider. "Explain what a derivative is" → animated tangent line that moves along a curve as the user drags a point. The visual shows the limit process.

Avoid: Static SVG with a fixed curve. It documents the result but doesn't show the mechanism of approximation.

Prompt signal: Any phrase containing "as x approaches", "rate of change", "area under", "converges to" → reach for interactive HTML, not static SVG.

learner-facing example prompt"I don't understand why the derivative of sin(x) is cos(x). Can you show me?" → HTML widget: animated unit circle + tangent line slider + live dy/dx readout
Computer science & algorithms
sorting, trees, graphs, memory, pointers
▼

Default: HTML stepper for algorithms (one step per click, array/tree redraws in SVG inside the stepper). "Show me how bubble sort works" → array of colored bars, step button highlights the comparison, bars swap with a smooth transition.

Memory / pointers: Illustrative SVG — boxes connected by literal arrow lines. A stack frame IS a rectangle. A pointer IS an arrow. Draw it.

Trees & graphs: SVG structural diagram with c-purple nodes and thin lines. Node click → sendPrompt about that traversal step.

learner-facing example prompt"Explain how quicksort partitions an array step by step" → HTML stepper: colored array, pivot highlighted in amber, left/right pointers moving, partition line drawing
Physics & chemistry
forces, waves, reactions, molecular structure
▼

Forces & motion: HTML with animated SVG. Show the vector as a colored arrow that scales with a slider. "What happens to acceleration when mass doubles?" → both variables are live.

Waves: HTML + Canvas or SVG path animation. Frequency and amplitude sliders. The wave redraws on every input event.

Molecular structure: Illustrative SVG with hardcoded physical colors (atom color conventions are universal — oxygen is red, hydrogen is white, carbon is black/gray). These must be hardcoded, not CSS variables, because they should not invert in dark mode.

Chemical reactions: HTML stepper showing reactants → transition state → products, with color transitions showing bond formation/breaking.

learner-facing example prompt"Show me how a sine wave changes when I increase frequency vs amplitude" → HTML: canvas path, two range sliders (frequency 1–10Hz, amplitude 0.1–2), live redraw at 60fps
Machine learning & AI
neural nets, training, embeddings, attention
▼

Neural network structure: SVG structural diagram — layers as columns of circles, weights as thin lines. Color encodes activation intensity (amber = high, gray = low).

Training process: HTML with Chart.js — live loss curve that animates downward as the "training" slider moves. Add a learning rate control to show overshooting.

Attention: Illustrative SVG — token row at bottom, one highlighted in amber, lines fanning up with stroke-width encoding weight. Make it interactive: click any token to become the query.

Embeddings: D3 scatter plot in HTML — words as dots in 2D projection, clusters visible. Hover shows the word, similar words cluster together.

learner-facing example prompt"I don't understand what attention weights actually represent" → SVG illustrative: 5-token row, one amber "query" token, 5 fan lines with stroke-width and opacity = weight, caption below: "thickness = how much 'sat' attends to each other token"
Biology & medicine
cells, physiology, genetics, anatomy
▼

Cell biology: SVG structural diagram — dashed outer membrane, labeled organelles as colored regions inside. Click any organelle → sendPrompt about its function.

Physiological processes (heart, lungs, kidneys): Illustrative SVG cross-section with physical colors. Animate fluid flow with CSS stroke-dasharray animation. A beating heart is 3 keyframes.

Genetics / DNA: Illustrative SVG — double helix shown as two parallel strands with rungs. Base pairs color-coded (A-T: amber, G-C: teal). Unzip animation in HTML.

Drug mechanisms: HTML stepper — receptor + molecule approaching, binding, conformational change, downstream effect. Each step is a panel.

learner-facing example prompt"Explain how the immune system responds to a pathogen" → HTML stepper: 5 stages (detection → APC activation → T-cell proliferation → antibody production → memory cells), each panel has SVG illustration + 2-line explanation
The pedagogical routing rule

Ask: does the learner need to document something or feel how it works? Documentation → flowchart/structural SVG. Feeling → illustrative SVG or interactive HTML. When in doubt, reach for the interactive version — a diagram you can operate creates 3× the recall of one you passively view.

03 — The Code

What Claude actually writes

Claude generates raw SVG markup or HTML fragments. Here is the exact anatomy of each output type, with every structural decision explained.

SVG is used for static diagrams, flowcharts, structural diagrams, and illustrative cross-sections. Every element has precise coordinates — the model calculates them from scratch.

/* The viewBox is always 680 wide — load-bearing. */
/* 1 SVG unit = 1 CSS pixel at the 680px container. */
<svg width="100%" viewBox="0 0 680 220">

  /* Arrow marker — always first in defs. */
  /* context-stroke makes the arrowhead inherit the line's color. */
  <defs>
    <marker id="arrow" viewBox="0 0 10 10" refX="8" refY="5"
             markerWidth="6" markerHeight="6" orient="auto-start-reverse">
      <path d="M2 1L8 5L2 9" fill="none" stroke="context-stroke"
            stroke-width="1.5" stroke-linecap="round"/>
    </marker>
  </defs>

  /* c-blue = CSS class injected by parent. Handles fill, stroke, */
  /* text color, AND dark mode automatically. Never hardcode hex. */
  /* node = clickable group with built-in hover effect. */
  <g class="node c-blue" onclick="sendPrompt('Tell me more about Input')">
    /* Box width = max(title_chars × 8, subtitle_chars × 7) + 24 */
    <rect x="60" y="80" width="160" height="56"
          rx="8" stroke-width="0.5"/>
    /* dominant-baseline="central" centers text on y — required. */
    <text class="th" x="140" y="100"
          text-anchor="middle" dominant-baseline="central">Input</text>
    <text class="ts" x="140" y="120"
          text-anchor="middle" dominant-baseline="central">tokenized text</text>
  </g>

  /* Connector — must not cross any other box interior. */
  /* If it would, use L-bend: M x1 y1 L x1 ymid L x2 ymid L x2 y2 */
  <line x1="220" y1="108" x2="298" y2="108"
        class="arr" marker-end="url(#arrow)"/>

  <g class="node c-teal" onclick="sendPrompt('How does the model process?')">
    <rect x="300" y="80" width="160" height="56" rx="8" stroke-width="0.5"/>

</svg>

The sendPrompt() bridge

Injected by the parent as: window.sendPrompt = text => parent.postMessage({type:'prompt', text}, '*'). This is the only communication channel between the widget and the chat. The parent listens via window.addEventListener('message',...) and injects the text as a new user message. No fetch, no WebSocket — just postMessage across the iframe boundary.

These are the absolute constraints the generated code must respect. Violating them produces invisible text, broken layouts, or security issues.

  • ✓
    viewBox="0 0 680 H" — always 680 wide. Changes rescale all coordinates and fonts.
  • ✓
    color: var(--color-text-primary) — CSS variables resolve for light AND dark mode.
  • ✗
    color: #333 — hardcoded hex. Invisible on dark background.
  • ✓
    class="c-blue" on SVG group — fill, stroke, text, dark mode all handled automatically.
  • ✗
    fill="#E6F1FB" on SVG rect — blue-50 in light mode, wrong in dark mode.
  • ✗
    localStorage.setItem(...) — blocked by sandbox. State lives in JS variables only.
  • ✗
    position: fixed — iframe sizes to content height. Fixed elements don't contribute, collapsing iframe to minimum.
  • ✗
    No <!DOCTYPE>, <html>, <head>, or <body> — fragments only, inside a parent document.
  • ✗
    No <!-- comments --> or /* comments */ — waste tokens, slow streaming.
  • ✓
    SVG text must have dominant-baseline="central" — without it, y is the baseline, not the visual center.
  • ✓
    Connector <path> elements must have fill="none" — SVG defaults to black fill, making paths into blobs.
  • ✓
    CDN: only cdnjs.cloudflare.com, esm.sh, cdn.jsdelivr.net, unpkg.com — CSP blocks all others silently.
  • ✓
    Box width = max(title_chars × 8, subtitle_chars × 7) + 24 — must be computed before drawing, never guessed.
  • ✗
    SVG text never auto-wraps. Every line break needs an explicit <tspan x="..." dy="1.2em">.

Tool choice strategy

Do not set tool_choice: "any" — that forces a visual on every response. Leave it as "auto" and let the system prompt's routing rules guide when Claude calls the tool. The model respects well-written routing instructions reliably. Forcing it overrides the model's judgment about when plain prose is the better answer.

Handling the tool call response — full SSE parser

async function* parseSSE(body) {
  const reader = body.getReader();
  const decoder = new TextDecoder();
  let buffer = '';
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop(); // last partial line stays in buffer
    for (const line of lines) {
      if (line.startsWith('data: ')) {
        try { yield JSON.parse(line.slice(6)); }
        catch {} // skip [DONE] sentinel
      }
    }
  }
}

async function consumeStream(response, onText, onWidget) {
  let toolJson = '', inTool = false, toolName = '';
  for await (const evt of parseSSE(response.body)) {
    if (evt.type === 'content_block_start') {
      if (evt.content_block.type === 'tool_use') {
        inTool = true; toolJson = '';
        toolName = evt.content_block.name;
      }
    }
    if (evt.type === 'content_block_delta') {
      if (!inTool && evt.delta.type === 'text_delta')
        onText(evt.delta.text);
      if (inTool && evt.delta.type === 'input_json_delta')
        toolJson += evt.delta.partial_json;
    }
    if (evt.type === 'content_block_stop' && inTool) {
      const params = JSON.parse(toolJson);
      onWidget(toolName, params); // { title, loading_messages, widget_code }
      inTool = false;
    }
  }
}

1
Model reasoning & code generation
Claude reads context, decides visual type, calculates coordinates, writes SVG or HTML as plain text.
LLM inference → tool call: show_widget(title, widget_code, loading_messages)
No image model. No canvas API. No external rendering service. The model generates raw markup the same way it generates Python or JSON — token by token from learned patterns. The quality of the visual comes entirely from the precision of the coordinate math inside the generated code. A rect at x=40 always lands 40px from the left. There is no rendering layer that "fixes" bad coordinates. The design system rules (coordinate math, color encoding, diagram type routing) are all applied during generation, not during rendering.
2
HTTP streaming via server-sent events
Response arrives token-by-token. Frontend accumulates the tool call block. Loading card shows until code is complete.
SSE stream → detect tool_use block start → accumulate widget_code → render on close
The connection is a standard HTTP response with Content-Type: text/event-stream. Each event is a JSON delta. The frontend detects when a tool_use content block begins (by type) and shows a loading card with the animated loading messages. The widget_code string accumulates as more tokens arrive. Only when the closing delimiter arrives does the frontend take the complete string and hand it to the iframe renderer. This is why code structure matters: style → content → script ensures the HTML is visually correct while scripts are still loading.
3
Sandboxed iframe
widget_code becomes the srcdoc of an iframe with strict sandbox flags. No access to parent page.
sandbox="allow-scripts allow-popups-to-escape-sandbox" — no allow-same-origin
Omitting allow-same-origin makes the iframe a cross-origin document — even though it's on the same domain. This means the widget code cannot access: cookies, localStorage, sessionStorage, IndexedDB, auth tokens, parent page DOM, window.location, or any browser storage. Model-generated code runs in a fully walled environment. The only escape hatch is window.postMessage(), which Claude uses via the injected sendPrompt() global to inject new user messages into the chat. A separate CSP header restricts external script sources to the allowlist: cdnjs.cloudflare.com, esm.sh, cdn.jsdelivr.net, unpkg.com.
4
CSS injection & theme resolution
Parent prepends a stylesheet defining all CSS variables and c-{ramp} class definitions. Dark mode is automatic.
--color-text-primary, --font-sans, c-blue, c-teal... resolve at paint time from prefers-color-scheme
Before the srcdoc renders, the parent prepends a <style> block containing: all --color-* and --font-* CSS custom properties (with @media prefers-color-scheme: dark overrides), all c-{ramp} class definitions (c-blue, c-teal, c-purple, etc.), the pre-built utility classes (node, arr, box, leader, t, ts, th), and the sendPrompt/openLink global function injections. The c-{ramp} classes use direct-child selectors (>) — nesting a group inside a c-blue group breaks it, as the inner shapes become grandchildren and fall out of the selector. Claude puts c-* on the innermost group containing the shapes.
5
Browser rendering: DOM → paint → composite
SVG/HTML parsed into DOM. CSS applied. Layout calculated. Paint commands issued to GPU.
viewBox="0 0 680 H" + width="100%" → 1:1 coordinate mapping at 680px container width
Identical to rendering any webpage. SVG elements become SVGElement DOM nodes with .x, .y, .width properties. CSS class selectors match them. The browser performs layout using the SVG coordinate system, applies fills and strokes from resolved CSS custom properties, and composites to a GPU layer. Scripts execute after full fragment parse. The iframe auto-sizes to the document's intrinsic height — which is why position:fixed breaks it (fixed elements don't contribute to scrollHeight, collapsing the iframe). The 1:1 coordinate guarantee: viewBox width 680 in a 680px container means every SVG unit is exactly 1 CSS pixel. Changing viewBox width rescales everything — font calibration, box widths, all break.

Color assignment rules

Encode meaning, not sequence

Don't cycle colors rainbow-style (step 1 = blue, step 2 = amber). Group nodes by category — all nodes of the same type share one color.

Use 2–3 colors per diagram

More colors = more visual noise. gray + purple + teal is cleaner than six ramps. Reserve blue/green/amber/red for semantic meaning (info/success/warning/error).

Physical properties → warm/cool

In illustrative diagrams: warm ramps (amber, coral, red) = heat/energy/pressure. Cool ramps (blue, teal) = cold/calm. Gray = inert structure.

Text on colored backgrounds

Use the 800 or 900 stop from the same ramp — never black or generic gray. Two-line boxes need different stops for title vs subtitle (800 title, 600 subtitle).

SVG text on colored backgrounds

Text on Blue-50 (#E6F1FB) must use Blue-800 (#0C447C) — not black. Light mode: 50 fill + 600 stroke + 800 title / 600 subtitle. Dark mode: 800 fill + 200 stroke + 100 title / 200 subtitle. The c-{ramp} classes handle both modes automatically when applied to the group.

function renderWidget(toolParams, container) {
  const { title, loading_messages, widget_code } = toolParams;

  // Show loading card immediately
  const card = document.createElement('div');
  card.className = 'widget-card loading';
  card.innerHTML = `<div class="loading-msg">${loading_messages[0] || 'Building visual…'}</div>`;
  container.appendChild(card);

  // Cycle through loading messages while code arrives
  let msgIdx = 0;
  const msgInterval = setInterval(() => {
    msgIdx = (msgIdx + 1) % loading_messages.length;
    const el = card.querySelector('.loading-msg');
    if (el) el.textContent = loading_messages[msgIdx];
  }, 1800);

  // Once widget_code is fully accumulated:
  clearInterval(msgInterval);
  card.classList.remove('loading');

  const iframe = document.createElement('iframe');
  iframe.sandbox = 'allow-scripts allow-popups-to-escape-sandbox';
  iframe.style.cssText = 'width:100%;border:none;display:block;border-radius:10px';
  iframe.title = title;

  const bridge = `<script>
    window.sendPrompt = t => parent.postMessage({type:'learner_prompt',text:t,widgetTitle:'${title}'},'*');
    window.addEventListener('load', () => {
      parent.postMessage({type:'iframe_resize',h:document.documentElement.scrollHeight},'*');
    });
    new ResizeObserver(() => {
      parent.postMessage({type:'iframe_resize',h:document.documentElement.scrollHeight},'*');
    }).observe(document.body);
  </script>`;

  iframe.srcdoc = `<style>${getLearnerCSS()}</style>${bridge}${widget_code}`;
  card.appendChild(iframe);

  // Auto-size + sendPrompt bridge
  window.addEventListener('message', e => {
    if (e.source !== iframe.contentWindow) return;
    if (e.data.type === 'iframe_resize')
      iframe.style.height = (e.data.h + 8) + 'px';
    if (e.data.type === 'learner_prompt')
      sendToAgent(e.data.text, { contextWidget: e.data.widgetTitle });
  });
}
The key insight for learning

The most impactful design principle is the illustrative vs. flowchart split. When explaining a concept, the temptation is to draw boxes and arrows. The better answer is usually a spatial metaphor that shows the mechanism — attention weights as a fan of lines, gradient descent as a ball on a loss surface, recursion as a stack of frames. That's what makes a visual actually teach rather than just document. Prompt the model explicitly toward this pattern for conceptual explanations.

07 — Agentic System

Building the full agent loop

A learning companion is not a one-shot chatbot. It maintains conversation history, routes tool calls, tracks what the learner has seen, and uses every visual click as a signal about where understanding needs deepening.

Multi-turn conversation with widget context

The agent needs to carry the full conversation history on every request. When a learner clicks a node inside a diagram, the widget title is passed alongside the question — giving the model context about what diagram was being viewed.

// Agent state — lives in your app, not the model
const agentState = {
  history: [],        // full message array — grows with every turn
  activeWidgets: {},  // widgetTitle → { code, topic, renderedAt }
  learnerProfile: {
    name: '',
    subject: '',
    conceptsSeen: [],  // track what's been visualised
    strugglingWith: [] // inferred from repeated questions
  }
};

async function sendToAgent(userText, meta = {}) {
  // Augment message with widget context if coming from a click
  const messageContent = meta.contextWidget
    ? `[Viewing diagram: "${meta.contextWidget}"] ${userText}`
    : userText;

  agentState.history.push({ role: 'user', content: messageContent });

  const response = await fetch('https://api.anthropic.com/v1/messages', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'x-api-key': YOUR_API_KEY,
      'anthropic-version': '2023-06-01'
    },
    body: JSON.stringify({
      model: 'claude-sonnet-4-20250514',
      max_tokens: 8192,
      stream: true,
      system: buildSystemPrompt(agentState.learnerProfile),
      tools: [SHOW_WIDGET_TOOL],
      messages: agentState.history  // full history every time
    })
  });

  let assistantText = '';
  const assistantBlocks = [];

  await consumeStream(response,
    text => { assistantText += text; appendChatText(text); },
    (toolName, params) => {
      assistantBlocks.push({ type: 'tool_use', name: toolName, input: params });
      renderWidget(params, chatContainer);
      // Track what's been shown to this learner
      agentState.activeWidgets[params.title] = { code: params.widget_code, shownAt: Date.now() };
      agentState.learnerProfile.conceptsSeen.push(params.title);
    }
  );

  // Push assistant turn to history (required for multi-turn)
  agentState.history.push({
    role: 'assistant',
    content: [
      ...(assistantText ? [{ type: 'text', text: assistantText }] : []),
      ...assistantBlocks
    ]
  });
}

Learner profile — building understanding over time

As the agent observes which concepts trigger follow-up questions and which diagrams the learner clicks into, it can adjust the system prompt dynamically — spending more time on struggled concepts and less on mastered ones.

function buildSystemPrompt(learnerProfile) {

Common agentic patterns for learner platforms

Pattern: concept → visual → quiz
Explain, show, then test understanding
▼

The most effective learning loop: Claude explains a concept in prose, generates a visual, then asks a Socratic question at the end. The learner's answer goes back into the conversation, and the agent decides whether to go deeper or advance.

system prompt additionAfter every concept explanation with a visual, end your response with a single Socratic question that tests whether the learner understood the mechanism — not just the definition. Wait for their answer before proceeding. If they answer correctly, acknowledge it briefly and offer to go deeper. If not, generate a different visual that approaches the same concept from a different angle.
Pattern: progressive disclosure
Start simple, add complexity on click
▼

For complex topics (neural networks, organic chemistry, quantum mechanics), the first diagram should be deliberately simplified. The full complexity lives behind sendPrompt() clicks on each component. This prevents the learner from being overwhelmed and gives them agency over the depth of exploration.

system prompt additionFor complex multi-component topics, always start with an overview diagram showing 3-4 high-level components only. Keep subtitles to 4 words maximum. Put the depth in the onclick sendPrompt questions — make each one invite the learner to zoom into that component specifically. The detail diagram for each component comes only when they click.
Pattern: multi-representation
Same concept, different visual encodings
▼

Research shows that learners who encounter the same concept in multiple visual formats (equation, graph, spatial metaphor, real-world analogy) retain it significantly longer. The agent can explicitly cycle through representations when it detects confusion.

system prompt additionIf a learner asks the same question a second time, or says they still don't understand after seeing a diagram, do not regenerate the same diagram. Instead, choose a completely different visual representation of the same concept — switch from structural to illustrative, from static SVG to interactive HTML, from abstract to concrete example. Every re-explanation must use a different visual encoding.
Pattern: comparison scaffolding
Show difference, not just definition
▼

Learners understand concepts best in contrast. "What is a stack?" is harder to answer than "How is a stack different from a queue?". The agent should default to comparative visuals that show both options simultaneously.

system prompt additionWhen a learner asks "what is X?" for any data structure, algorithm, or concept that has a natural counterpart, generate a side-by-side SVG structural diagram showing X and its complement (stack/queue, array/linked list, TCP/UDP, supervised/unsupervised). The visual difference teaches both concepts simultaneously.
